# 文档资源管理

> 模块目录：`system/document-resource-management/` · 资源清单：`manifest/document_resource_manifest.json`

## 1. 模块定位与目标

本模块把“文档”作为系统资源进行管理，而不是把文档当成附属说明。对于软硬件深度耦合的系统，文档本质是**契约、决策、约束、验证证据与知识资产**的载体。

文档资源管理的核心目标：

1. 把软硬件交互入口问题转化为可追踪、可审查、可版本化的文档资源。
2. 按优先级组织系统级问题，使架构设计从最高风险、最强约束处展开。
3. 建立“问题 → 决策 → 设计 → 实现 → 验证 → 现场维护”的追溯链。
4. 让文档和代码、配置、测试、硬件描述共享同一套资源治理规则。
5. 防止关键硬件系统工程问题只停留在口头经验或散落注释中。

**边界**：

- 不负责具体驱动实现，驱动设计见 `driver/*`。
- 不负责代码版本控制流程本身，但定义文档资源纳入版本控制的规则。
- 不替代硬件设计文档、芯片手册或供应商资料，只管理本项目内的文档资源条目。
- 不把文档数量作为目标，目标是**关键契约完整、优先级明确、状态可审计**。

**服务场景**：汽车域控、工业网关、IoT 边缘节点、AI 边缘部署、工业机器人，以及所有涉及 SoC、FPGA、Linux、RTOS、裸机、C/C++/Rust 混编的系统级项目。

---

## 2. 需求与约束

| 类别 | 要求 |
|------|------|
| 完整性 | P0 资源必须覆盖启动、时钟、地址、寄存器、中断、DMA、时间、故障、安全 |
| 优先级 | 所有文档资源必须标注 `P0/P1/P2/P3`，并说明排序理由 |
| 单一数据源 | 寄存器、地址、中断、设备树、版本矩阵等必须指定 source of truth |
| 可追溯 | 每条资源必须能追到设计文档、实现模块和验证证据 |
| 可审计 | 文档状态、版本、owner、审批人、变更记录必须可查 |
| 可执行 | 清单应能被 CI 检查，不能只是自然语言描述 |
| 稳定性 | 基线后的 P0 文档变更必须走架构变更流程 |
| 兼容性 | 文档资源必须绑定硬件版本、固件版本和场景版本 |

## 3. 架构设计

### 3.1 文档作为系统资源

系统资源不只有 CPU、内存、中断、DMA、时钟和功耗。文档也是一种资源，因为它决定：

- 系统边界如何定义；
- 硬件契约如何被解释；
- 软件抽象如何被批准；
- 故障行为如何被验证；
- 新人如何建立正确硬件思维；
- 量产问题是能定位，还是变成不可复现事故。

因此，文档资源必须与代码资源同等对待，拥有：

```text
唯一 ID、owner、优先级、状态、版本、依赖、消费者、验证方式、生命周期
```

### 3.2 优先级模型

| 优先级 | 定义 | 判断标准 | 典型内容 |
|---|---|---|---|
| `P0` | 架构基石 | 不解决会导致系统不可启动、不可控、数据损坏、安全失效或不可恢复故障 | 复位、时钟、地址空间、寄存器语义、中断协议、DMA/cache、故障安全、权限隔离 |
| `P1` | 系统闭环 | 不解决会导致系统可运行但不可验证、不可诊断、不可实时保证、不可维护 | 时间预算、可观测性、配置单一源、版本兼容、验证矩阵 |
| `P2` | 工程效率 | 不解决不会立即造成系统错误，但会显著降低开发、评审、量产维护效率 | 自动生成、模板规范、知识库、问题复盘、工具链 |
| `P3` | 优化增强 | 属于性能、成本、体验层面的进一步优化 | 功耗调优、带宽 QoS、高级 trace、自动分析 |

### 3.3 文档资源分类

| 分类 | 说明 | 示例 |
|---|---|---|
| 契约类 | 定义软硬件不可违反的接口规则 | Memory Map、寄存器契约、中断契约、DMA 契约 |
| 决策类 | 记录为什么选择某种架构方案 | ADR、技术权衡表、安全状态决策 |
| 设计类 | 描述模块内部结构和行为 | 启动流程、时钟电源状态机、故障恢复流程 |
| 验证类 | 证明设计是否满足约束 | HIL 测试、中断延迟测试、CDC 检查报告 |
| 配置类 | 定义版本化配置和依赖关系 | 设备树、寄存器生成源、硬件版本兼容矩阵 |
| 运维类 | 支撑量产后诊断和知识沉淀 | crash dump 格式、现场问题清单、复盘报告 |

### 3.4 文档资源元模型

每条文档资源至少包含以下字段：

| 字段 | 说明 |
|---|---|
| `id` | 全局唯一资源编号 |
| `title` | 文档资源名称 |
| `priority` | `P0/P1/P2/P3` |
| `category` | 契约、决策、设计、验证、配置、运维 |
| `owner` | 责任人或责任角色 |
| `status` | `draft/review/baseline/frozen/deprecated/archived` |
| `version` | 资源版本 |
| `source_of_truth` | 单一数据源路径或来源 |
| `path` | 文档或清单路径 |
| `dependencies` | 依赖的其他资源 |
| `consumers` | 消费该资源的模块 |
| `validation` | 验证方式 |
| `security_level` | 公开、内部、受限、安全相关 |
| `change_control` | 变更审批级别 |

### 3.5 生命周期状态机

```text
draft -> review -> approved -> baseline -> frozen -> deprecated -> archived
```

| 状态 | 含义 | 允许操作 |
|---|---|---|
| `draft` | 初稿，可讨论 | 修改内容、补充问题 |
| `review` | 评审中 | 评审意见记录、影响分析 |
| `approved` | 已批准但未基线 | 进入发布流程 |
| `baseline` | 当前有效基线 | 只允许受控变更 |
| `frozen` | 版本冻结，用于发布或认证 | 禁止普通修改 |
| `deprecated` | 已被替代但仍需保留 | 只允许标注替代关系 |
| `archived` | 归档 | 只读保存 |

## 4. 按优先级排列的系统文档资源清单

### 4.1 `P0`：架构基石资源

这些资源是软硬件交互的最小闭环。没有它们，后续 HAL、驱动、RTOS、内核、AI、FPGA、场景集成都缺少可靠基础。

| ID | 文档资源 | 必须回答的问题 | 主要输出物 | 消费模块 |
|---|---|---|---|---|
| `DOC-SYS-000` | 文档资源治理规则 | 文档如何编号、分级、评审、变更、归档？谁是 owner？什么算单一数据源？ | 资源元模型、状态机、变更规则 | `system/*` |
| `DOC-HWIF-001` | 上电复位与启动入口 | 复位源、启动介质、复位向量、栈初始化、`.data/.bss`、多核启动、启动失败如何定义？ | 复位流程图、启动时序图、启动失败矩阵 | `boot/startup` |
| `DOC-HWIF-002` | 时钟、电源与复位域 | 时钟树、PLL lock、电源域、上掉电顺序、唤醒恢复、动态调频约束如何定义？ | 时钟树、电源域图、唤醒恢复清单 | `platform/clock-power`、`platform/soc-arch` |
| `DOC-HWIF-003` | 地址空间与 Memory Map | 地址归属、权限、cache 属性、DMA 可见性、Secure/Non-secure、保留区如何定义？ | Memory Map 表、地址权限矩阵 | `memory/memory-model`、`platform/*` |
| `DOC-HWIF-004` | 寄存器访问语义 | 字段属性、副作用、读改写风险、访问宽度、写顺序、屏障、原子性如何定义？ | 寄存器契约、字段访问表、写序列规范 | `driver/bit-register`、`driver/pac-hal` |
| `DOC-HWIF-005` | 中断、异常与事件入口 | IRQ 优先级、触发方式、清除协议、共享中断、中断风暴、上下文约束、SError/NMI 如何处理？ | 中断资源表、优先级矩阵、延迟预算 | `concurrency/interrupt-critical`、`kernel/irq` |
| `DOC-HWIF-006` | DMA、Cache 与数据所有权 | buffer 归属、方向、cache clean/invalidate、descriptor 顺序、IOMMU、错误恢复如何定义？ | DMA 契约、buffer 状态机、cache 策略表 | `memory/resource-scheduling`、`memory/memory-barrier` |
| `DOC-HWIF-007` | 时间、实时性与确定性 | deadline、WCET、关中断时间、总线延迟、抖动、跨时钟域、端到端延迟如何预算？ | 实时任务表、延迟预算表、时序报告 | `concurrency/*`、`fpga/timing`、`kernel/realtime` |
| `DOC-HWIF-008` | 故障、可靠性与功能安全 | 故障分类、检测、隔离、恢复、安全状态、watchdog、ECC/CRC、FMEA 如何定义？ | 故障矩阵、FMEA 表、安全状态定义 | `kernel/security`、`system/*` |
| `DOC-HWIF-009` | 权限、安全与隔离 | MPU/MMU、TrustZone、IOMMU、调试口、固件验签、防回滚、安全日志如何定义？ | 权限矩阵、威胁模型、安全边界图 | `kernel/security`、`foundation/misra` |

### 4.2 `P1`：系统闭环资源

这些资源决定系统能否被验证、诊断、维护和稳定演化。

| ID | 文档资源 | 必须回答的问题 | 主要输出物 | 消费模块 |
|---|---|---|---|---|
| `DOC-SYS-010` | 可观测、调试与量产维护 | 日志、trace、时间戳、crash dump、计数器、量产测试、校准数据如何定义？ | trace 点位表、dump 格式、量产测试清单 | `foundation/debug-log`、`system/*` |
| `DOC-SYS-011` | 单一数据源与配置管理 | 寄存器、设备树、链接脚本、版本矩阵是否只有一个源头？生成物如何校验？ | 生成源清单、配置兼容矩阵 | `platform/devicetree-bsp`、`driver/*` |
| `DOC-SYS-012` | 验证与评审证据 | 文档是否通过 schema 校验、链接检查、追溯检查、评审签字、测试覆盖？ | 验证矩阵、评审记录、证据索引 | `system/document-resource-management` |
| `DOC-SYS-013` | 资源预算与容量规划 | CPU、内存、中断、DMA、带宽、功耗、栈、队列、时限是否有预算表？ | 资源预算表、容量规划表 | `memory/*`、`kernel/*` |

### 4.3 `P2`：工程效率资源

这些资源不一定决定系统能否启动，但决定项目能否长期演进。

| ID | 文档资源 | 必须回答的问题 | 主要输出物 | 消费模块 |
|---|---|---|---|---|
| `DOC-SYS-014` | 文档模板与写作规范 | 模块文档统一章节、表格风格、引用规则、术语表如何维护？ | 模板、术语表、写作规范 | 全项目 |
| `DOC-SYS-015` | 工具链与自动生成 | 如何从 SVD/IP-XACT/YAML 生成寄存器头、设备树片段、索引和清单？ | 生成器说明、CI 检查规则 | `driver/*`、`platform/*` |
| `DOC-SYS-016` | 问题复盘与知识沉淀 | 现场问题、设计缺陷、验证遗漏如何进入知识库并防复发？ | 复盘报告、防复发清单 | `system/*` |

### 4.4 `P3`：优化增强资源

这些资源用于进一步优化性能、成本、功耗和可维护性。

| ID | 文档资源 | 必须回答的问题 | 主要输出物 | 消费模块 |
|---|---|---|---|---|
| `DOC-SYS-017` | 性能、功耗与带宽调优 | cache 分区、DMA 带宽、CPU 核隔离、DVFS、唤醒延迟如何优化？ | 调优报告、QoS 配置说明 | `platform/*`、`kernel/*` |
| `DOC-SYS-018` | 高级诊断与自动分析 | trace 自动分析、异常聚类、现场遥测、预测性维护如何设计？ | 诊断规则、遥测模型 | `ai/*`、`system/*` |

## 5. 接口设计

本模块的机器可读接口是：

```text
manifest/document_resource_manifest.json
```

### 5.1 清单字段

| 字段 | 类型 | 说明 |
|---|---|---|
| `schema_version` | string | 清单 schema 版本 |
| `priority_model` | array | 优先级定义 |
| `resources` | array | 文档资源条目 |
| `lifecycle` | array | 文档生命周期状态 |
| `required_fields` | array | 每条资源必须包含的字段 |
| `change_control` | object | 各优先级变更审批规则 |

### 5.2 资源条目字段

每条 `resources[]` 条目包含：

- `id`
- `title`
- `priority`
- `category`
- `status`
- `owner`
- `source_of_truth`
- `path`
- `questions`
- `outputs`
- `consumers`
- `validation`
- `security_level`

### 5.3 优先级使用规则

1. 新增模块前，先检查是否存在对应 `P0` 文档资源。
2. 修改 `P0` 资源必须触发架构评审。
3. `P1` 资源变更必须影响分析。
4. `P2/P3` 资源可由 owner 维护，但必须保持追溯链完整。
5. 发布版本必须冻结所有 `P0` 和 `P1` 基线资源。

## 6. 关键流程与时序

### 6.1 新增文档资源

```text
识别问题 -> 分配 ID -> 判定优先级 -> 指定 owner -> 建立 source of truth
-> 编写 -> 评审 -> 基线 -> 更新消费模块 -> CI 校验
```

### 6.2 变更文档资源

```text
变更请求 -> 影响分析 -> 优先级判定 -> 审批 -> 更新文档/清单
-> 更新依赖资源 -> 更新验证证据 -> 发布新基线
```

### 6.3 问题进入文档资源库

一个现场问题或设计缺陷进入资源库时，必须回答：

1. 它暴露了哪个 `P0/P1` 问题？
2. 现有文档资源是否覆盖？
3. 未覆盖时新增还是补充？
4. 是否需要新增验证项？
5. 是否需要冻结旧版本？
6. 是否需要同步到场景文档？

## 7. 设计决策与权衡

| 决策点 | 选择 | 备选 | 理由 |
|---|---|---|---|
| 文档是否作为资源 | 是 | 普通文件夹 | 文档承载契约，必须治理 |
| 优先级层级 | 四级 `P0-P3` | 仅高中低 | 四级更适合架构基线与工程效率分层 |
| 机器接口 | JSON 清单 | 纯 Markdown 表格 | JSON 可被 CI 校验和工具消费 |
| 单一数据源 | 强制指定 | 允许缺失 | 缺失会导致文档与硬件配置漂移 |
| P0 变更 | 架构评审 | owner 自行修改 | P0 影响系统正确性和安全 |
| 文档粒度 | 一个主题一个资源 | 大合集 | 便于追溯、审批、复用 |
| 状态管理 | 显式生命周期 | 只看 Git 历史 | Git 不表达批准、冻结、废弃状态 |

## 8. 性能指标（KPI）

- `P0` 文档资源覆盖率：`100%`。
- 新增模块前的文档资源检查覆盖率：`100%`。
- 文档资源 ID 唯一率：`100%`。
- `path` 链接有效率：`100%`。
- `source_of_truth` 缺失数：`P0=0`、`P1=0`。
- 基线文档中过期条目比例：目标 `< 5%`。
- 每次发布前 `P0/P1` 资源冻结完成率：`100%`。
- 变更请求影响分析完成率：`100%`。
- CI 校验失败必须在合并前清零。

## 9. 可靠性设计

- 清单 schema 校验：防止字段缺失、优先级非法、ID 重复。
- 路径校验：防止文档移动到新位置后链接失效。
- 依赖校验：防止资源依赖不存在或状态不兼容。
- 状态校验：防止 `draft` 资源被消费模块当作 `baseline` 引用。
- 冻结校验：发布版本冻结后禁止普通修改。
- 替代关系校验：`deprecated` 资源必须指向替代资源。
- 审批校验：`P0` 修改必须具备架构评审记录。

---

## 10. 安全设计

- 安全相关文档标记 `security_level=restricted` 或 `safety-related`。
- 威胁模型、密钥存储、调试口、安全启动等资源限制访问范围。
- 固件版本、硬件版本、安全补丁记录必须进入资源追踪链。
- 安全相关的 `P0` 文档变更必须保留审批证据。
- 现场诊断数据若包含敏感信息，必须脱敏后进入知识库。
- 发布包只携带必要文档，避免泄露内部安全边界细节。

## 11. 测试与验证策略

| 验证项 | 方法 | 通过条件 |
|---|---|---|
| schema 校验 | JSON 解析 + 字段检查 | 无非法字段、无缺失必填项 |
| ID 唯一性 | 脚本扫描 | 无重复 `id` |
| 优先级完整性 | 脚本统计 | `P0-P3` 分布符合预期 |
| 路径有效性 | 文件系统检查 | 所有 `path` 存在 |
| 依赖有效性 | 图检查 | 无悬空依赖、无循环依赖 |
| 消费模块有效性 | 路径检查 | `consumers` 指向有效模块或通配域 |
| 状态合法性 | 状态机校验 | 状态只能取允许值 |
| 文档链接检查 | Markdown 链接扫描 | 链接目标存在 |
| 发布冻结检查 | 版本基线检查 | `P0/P1` 均为 `baseline/frozen` |
| 评审证据检查 | ADR / 记录检查 | `P0` 变更存在评审记录 |

### 12.3 推荐使用方式

1. 架构评审前读取 `P0` 清单。
2. 模块设计前检查 `consumers` 是否包含目标模块。
3. 代码评审时检查实现是否满足文档契约。
4. 发布前冻结 `P0/P1` 资源。
5. 现场问题复盘后更新 `DOC-SYS-016` 或对应契约资源。

## 关联模块

- `memory/memory-model`：地址、对齐、端序、内存段契约。
- `memory/memory-barrier`：MMIO 可见性、屏障、cache 一致性。
- `memory/resource-scheduling`：内存资源预算、配额、所有权。
- `driver/bit-register`：寄存器访问语义的落地实现。
- `boot/startup`：复位与启动入口的落地实现。
- `concurrency/interrupt-critical`：中断与临界区约束。
- `platform/clock-power`：时钟、电源、复位域。
- `kernel/security`：权限、隔离、安全状态。
- `system/*`：五大场景对文档资源基线进行集成消费。
