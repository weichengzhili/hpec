# 系统问题链

> 这是 HPEC 项目的总纲。整个项目的领域划分、模块设计、接口定义，都围绕这条问题链展开。
> 它不是概念分类，而是一条因果链：**每一环的答案，是下一环的地基。**
> 每个模块「解决什么问题 + 边界标准 + 位置」，见 [模块问题定义](模块问题定义.md)。

---

## 0. 为什么是问题链，不是模块清单

一个嵌入式系统不是"内存 + 中断 + 驱动 + 内核"的叠加，而是一条链：

```text
上电 → 时钟复位稳定 → 启动 → 建立可见性 → 控制硬件 → 响应事件
→ 搬运数据 → 处理并发 → 调度资源 → 处理故障 → 观测证明 → 演进
```

任何一个模块，如果脱离了它在这条链上的位置，就会变成孤立的概念。反过来，任何一个环节没有闭合，它下游的所有环节都建立在沙子上。

本问题链的目标是回答一个总命题：

> 一个事件进入系统后，系统如何在正确的时间、用正确的数据、在正确的权限下，做出可被验证的正确响应——并且在异常时仍然可控？

每一环都按六个维度展开：

1. 一句话本质；
2. 在本项目（RK3588 + FPGA + Linux PREEMPT_RT + C/C++/Rust）里的具体体现；
3. 不闭合的后果（具体，不是笼统的"系统会坏"）；
4. 必须回答的子问题；
5. 设计动作与验证手段；
6. 挂靠的模块。

---

## 1. 问题链图谱

```text
[0 物理真相] → [1 启动] → [2 可见性] → [3 控制] → [4 事件]
        ↘                                      ↓
                                    [5 数据] → [6 并发] → [7 资源]
                                                          ↓
                                          [10 演进] ← [9 证据] ← [8 故障]
```

三个闭环贯穿其中：

- **正常态闭环**：`4 事件 → 5 数据 → 6 并发 → 7 资源 → 4`
- **故障态闭环**：`8 故障 → 9 证据 → 10 演进 → 8`（问题回流，改变规则）
- **演进态闭环**：`10 演进 → 0~9`（任何变更反向冲击全链）

## 2. 每一环的展开

### 环 0：物理真相 —— 你的软件运行在多少个时钟域和电源域之上？

**本质**：一切正确性的地基是"此刻哪个时钟在跑、哪个电源域活着、DDR 训练完成没有、复位释放没有"。

**具体体现**：

- RK3588 的 CRU 从 24MHz 晶振派生出 CPU（A76/A55 分簇）、NPU、GPU、DDR、各类外设的时钟；每个外设的时钟都可以被门控（gate）。
- 电源域相互独立：一个电源域掉电后，该域内寄存器回到复位值、片上 SRAM 内容丢失。
- DDR 必须经过上电训练（memory training）后才可读写，训练发生在启动早期。
- FPGA 侧有独立时钟域，与 SoC 之间是跨时钟域接口，需要同步器或异步 FIFO。

**不闭合的后果**：

- 在外设时钟被 gate 掉时写它的寄存器：总线无应答或超时，而不是返回一个干净的错误码。
- 在 DDR 训练完成前访问 DDR：启动直接死在 DDR bin 阶段，没有日志。
- 把一个 24MHz 外设当成和 CPU 同频去连续读状态：读到中间态，得到错误的值。

**必须回答的子问题**：

1. 每个外设的时钟默认是开还是关？谁来开？开和关的时序约束是什么？
2. 每个电源域掉电后，哪些寄存器和内存要重新初始化？
3. DDR 训练的触发点、完成标志、失败回退是什么？
4. 每个复位域释放的先后顺序？复位释放后是否需要同步等待？
5. FPGA 与 SoC 的时钟相位关系、复位同步由谁负责？

**设计动作与验证**：

- 建立 CRU 时钟树表 + 电源域图 + 复位域表，作为所有驱动的唯一前置契约。
- 任何外设驱动的第一段代码是"确保时钟开、复位已释放、电源域上电"，而不是直接写寄存器。
- 验证：在时钟 gate 状态访问外设，确认行为可预测（超时/异常），而不是挂死。

**模块**：`../../platform/soc-arch`、`../../platform/clock-power`、`../../boot/startup`、`../../fpga/cdc`

### 环 1：启动 —— 从"随机态"到"可信运行态"，中间没有安全网

**本质**：软件第一条指令执行时，世界还没就绪。启动的每一级都是"建立信任 → 交棒给下一级"。

**具体体现**：

- RK3588 多级启动：Mask ROM → DDR bin → TF-A/OPTEE → U-Boot → Linux。
- `.data` 段拷贝、`.bss` 段清零必须发生在任何 C 代码运行之前。
- 安全启动的签名校验链、A/B 启动槽、防版本回滚。
- 多核：A76/A55 从核由主核释放，每个核的栈、TLS、per-CPU 数据要分别初始化。

**不闭合的后果**：

- `.bss` 没清零：全局变量初值随机，表现为偶发、不复现、跟温度相关。
- DDR 训练失败却继续启动：Linux 起来后随机 panic。
- 安全启动链断掉：刷入被篡改的镜像时系统无感知。

**必须回答的子问题**：

1. 从复位向量到 `main`，每一级如何校验"我拿到的下一级镜像是可信的"？
2. 谁负责 DDR 训练？训练失败如何回退？
3. A/B 槽的回退判定条件是什么？什么情况算"启动失败"？
4. 从核启动如何不破坏主核已经建立的页表和内存布局？
5. 启动失败时系统进入什么状态？早期日志怎么输出？

**设计动作与验证**：

- 产出启动时序图 + 信任链图 + 启动失败回退矩阵。
- 启动自检：`.data` 校验和、栈水位检测、DDR ECC 状态检查。
- 验证：冷启动、热启动、看门狗复位、软件复位四种路径都走一遍，确认状态一致。

**模块**：`../../boot/startup`、`../../platform/uboot`、`../../platform/soc-arch`

### 环 2：可见性 —— 你看到的地址，是不是硬件真正的地址？

**本质**：软件不是直接操作硬件，而是操作"经过 MMU/SMMU/cache 属性翻译后的一个视图"。

**具体体现**：

- RK3588 有 SMMU（IOMMU），DMA/NPU/VPU 访问内存要走 SMMU 映射。
- cache 属性（normal / device / strongly-ordered）决定 MMIO 和 DMA 内存的可见性。
- Memory Map 中 MMIO、DDR、SRAM、保留区权限各不相同。

**不闭合的后果**：

- MMIO 被标成 cacheable：寄存器读写落在 cache 里，外设收不到命令、CPU 读不到真实状态。
- DMA 没配 SMMU：外设访问错误的物理地址，破坏任意内存。
- CPU 和 NPU 用不同的地址视图：同一块 buffer 两边看到的不是同一个东西。

**必须回答的子问题**：

1. 每段地址的 owner、权限、cache 属性、DMA 可见性是什么？
2. 哪些区域 CPU 可见但 DMA 不可见？哪些反过来？
3. SMMU 的映射粒度、缺页和越权行为是什么？
4. NPU/VPU/DMA 的物理地址如何和 CPU 虚拟地址对应？
5. 保留区访问会怎样？是否产生可捕获的异常？

**设计动作与验证**：

- 产出 Memory Map 表 + 地址权限矩阵 + SMMU 配置契约。
- 所有 DMA 驱动先声明"我用的 buffer 在哪个属性区"，再谈搬运。
- 验证：故意把 MMIO 标错 cache 属性，确认能检测出来。

**模块**：`../../memory/memory-model`、`../../memory/memory-barrier`、`../../kernel/dma`、`../../platform/soc-arch`

---

### 环 3：控制 —— 写寄存器 ≠ 硬件已执行

**本质**：写寄存器只是投递一个总线事务。硬件的状态变化有延迟、有副作用、有前置条件。

**具体体现**：

- RK3588 外设寄存器有 RW / RO / WO / W1C / RC 等访问属性。
- 配置寄存器写入后要等 READY/ACK；命令寄存器写即触发动作。
- 有的状态位读一次就自动清除。

**不闭合的后果**：

- 写完配置没等 READY 就认为生效：外设还在旧配置下工作。
- 对 W1C 字段做 read-modify-write：误清其他中断标志。
- 写完命令没等完成位：下一笔数据覆盖上一笔。

**必须回答的子问题**：

1. 每个寄存器的读写属性、复位值、副作用、生效延迟是什么？
2. 哪些操作需要读回确认？哪些需要等完成位？完成位会不会自动清除？
3. 多写者（中断 + 任务）同时写一个寄存器如何仲裁？
4. 写顺序是否被硬件要求固定？是否需要内存屏障？

**设计动作与验证**：

- 产出寄存器契约表，由 SVD/IP-XACT 生成，禁止手写。
- 每个写序列定义"写 → 确认 → 生效"的闭环。
- 验证：对每个关键外设做 write → readback 一致性测试。

**模块**：`../../driver/bit-register`、`../../driver/pac-hal`、`../../driver/hal`、`../../foundation/result`

---

### 环 4：事件 —— 外部世界如何打断你，而你如何不被打死

**本质**：中断是硬件在任何时刻都能改变软件控制流的方式，它不是函数调用。

**具体体现**：

- GIC-600 管理 SPI/PPI/SGI，涉及优先级、屏蔽、CPU affinity、触发方式（边沿/电平）。
- PREEMPT_RT 把中断线程化，硬中断只做"记录 + 唤醒线程"。
- GPIO、DMA 完成、NPU 完成、网络、定时器都是中断源。

**不闭合的后果**：

- 电平中断没在 ISR 里清 source：中断风暴，主循环被饿死。
- 共享中断线没查清是谁触发：误处理，真实源没被服务。
- ISR 里读 64 位计数器高低 32 位跨拍：时间戳错乱。
- 中断里拿锁，锁又被更高优先级中断占用：死锁。

**必须回答的子问题**：

1. 每个 IRQ 的触发方式、清除协议、优先级、CPU affinity 是什么？
2. 上下半部边界在哪？哪些操作必须在硬中断里做？
3. 关中断/屏蔽的最长时间是多少？是否满足实时预算？
4. 中断风暴如何检测和降级？

**设计动作与验证**：

- 产出中断资源表 + 优先级矩阵 + 延迟预算。
- ISR 只做"读真相 + 清事件 + 投递"，重活交下半部/工作队列。
- 验证：中断风暴注入、延迟测量、优先级反转测试。

**模块**：`../../platform/gic`、`../../kernel/irq`、`../../kernel/realtime`、`../../concurrency/interrupt-critical`

---

### 环 5：数据 —— 数据流不是拷贝，是所有权迁移

**本质**：DMA/NPU/VPU 是独立总线主设备，能绕过 CPU 直接改内存。buffer 有物理所有权。

**具体体现**：

- MIPI-CSI 采集 → ISP → DDR → NPU 输入 → NPU 输出 → DDR → 显示/网络，这是一条零拷贝流水线。
- 每段 DMA 有 channel，cache 一致性（clean/invalidate）决定数据可见性。
- descriptor 环的 head/tail 更新顺序靠内存屏障保证。

**不闭合的后果**：

- CPU 写完数据还在 cache（dirty line），DMA 从 DDR 读到旧数据。
- DMA 写完，CPU 读到的还是旧 cache 行。
- buffer 还给池子，DMA 还在写：内存被静默破坏。
- descriptor 半新半旧：DMA 读到错误的描述符。

**必须回答的子问题**：

1. 流水线每一段 buffer 的 owner 是谁？何时 clean/invalidate？
2. buffer 池的分配/归还协议是什么？如何防 DMA 释放后仍被访问？
3. descriptor 环的同步点在哪？用什么内存屏障？
4. 一条流水线的端到端延迟和吞吐预算是什么？

**设计动作与验证**：

- 产出 buffer 所有权状态机 + cache 维护策略表。
- 零拷贝流水线：一帧数据全程不拷贝，只转移所有权。
- 验证：cache 一致性测试、DMA 超时/错误注入、所有权审计。

**模块**：`../../memory/resource-scheduling`、`../../memory/memory-barrier`、`../../platform/dma-engine`、`../../platform/mipi-csi`、`../../ai/vision-pipeline`

---

### 环 6：并发 —— 硬件没有顺序一致性，顺序是软件买来的

**本质**：CPU、DMA、NPU、中断、看门狗、调试器并发执行，硬件不保证它们看到同一份真相。

**具体体现**：

- 多核 A76/A55 + NPU + DMA 同时访问共享 buffer。
- 锁、原子操作、内存屏障、RCU、自旋锁。
- 优先级反转、中断里拿锁导致的死锁。

**不闭合的后果**：

- 没有屏障，编译器/CPU 重排 MMIO 访问：配置顺序被打乱。
- 共享结构无锁但边界不清：数据竞争，偶发且难复现。
- 持锁进中断，中断里拿同一把锁：死锁。
- 低优先级持锁、高优先级等锁：优先级反转，实时任务超时。

**必须回答的子问题**：

1. 每个共享结构的访问协议：无锁（有明确边界）还是加锁（有持有上界）？
2. 哪些内存需要屏障？MMIO、DMA buffer、普通共享变量各用什么内存序？
3. 锁的持有时间上界是多少？是否允许优先级继承？
4. NPU 和 CPU 共享 buffer 的同步点在哪？

**设计动作与验证**：

- 产出内存序分类（MMIO / DMA buffer / 共享变量）+ 锁纪律清单。
- 短临界区 + 关中断/自旋锁，锁持有时间有上界。
- 验证：数据竞争检测、优先级反转测试、锁持有时间测量。

**模块**：`../../concurrency/interrupt-critical`、`../../concurrency/fsm`、`../../kernel/lock`、`../../memory/memory-barrier`

### 环 7：资源 —— 压力之下，谁先跑，谁等待，谁降级

**本质**：CPU 核、DDR 带宽、cache、PCIe、NPU 算力、功耗/热，都是有限资源，压力下必须有明确决策。

**具体体现**：

- CFS + 实时调度（PREEMPT_RT）、CPU affinity、核隔离。
- DDR 带宽被 AI 推理 + 8K 编解码 + 相机采集同时争抢。
- NPU 6TOPS 被多个推理模型分时/分片。
- DVFS 调频调压、热降频。

**不闭合的后果**：

- AI 推理高峰期 DDR 带宽被占满：实时 EtherCAT 任务抖动超标。
- 无核隔离：实时任务被普通任务抢占，错过 deadline。
- NPU 被单模型独占：多模型串行，端到端延迟爆炸。
- 热失控不降频：芯片损坏或系统重启。

**必须回答的子问题**：

1. 每个实时任务的 deadline、WCET、抖动预算是什么？
2. 哪些核给实时、哪些核给 AI/通用？cache 和 DDR 带宽如何分区？
3. NPU 如何多模型分时？优先级和抢占策略是什么？
4. 热/功耗预算和降频策略是什么？降频后实时任务还满足吗？

**设计动作与验证**：

- 产出资源预算表 + 核隔离/带宽分区配置。
- 实时任务绑定 + cache 分区 + DDR 带宽限流。
- 验证：压力测试下实时任务抖动测量、热降频测试。

**模块**：`../../kernel/scheduler`、`../../kernel/realtime`、`../../kernel/mm`、`../../platform/clock-power`、`../../platform/npu`、`../../ai/performance`

---

### 环 8：故障 —— 异常路径才是系统好坏的分水岭

**本质**：寄存器写失败、DMA 超时、内存位翻转、外设挂起，是常态边缘，不是意外。

**具体体现**：

- watchdog、DDR ECC、DMA 错误中断、NPU 挂起、温度越限。
- PREEMPT_RT 下故障处理不能破坏实时性。
- fail-safe / fail-operational（汽车域控、工业机器人）。

**不闭合的后果**：

- DMA 超时后 channel 半途状态，buffer 归属不明，软件死等。
- 看门狗复位后外设半途，重启不知道上次死在哪。
- 恢复动作本身也失败：系统无路可走。

**必须回答的子问题**：

1. 每个故障的检测、隔离、恢复、降级路径是什么？
2. 安全态（fail-safe）是什么？恢复失败时往哪走？
3. 看门狗复位后如何恢复现场（复位原因寄存器、dump）？
4. 哪些功能必须 fail-operational（不能停）？哪些可以 fail-silent？

**设计动作与验证**：

- 产出故障矩阵 + FMEA + 恢复策略表 + 安全态定义。
- 关键动作读回校验、超时、重试上限，超限降级而不是死等。
- 验证：故障注入、看门狗复位恢复、双故障测试。

**模块**：`../../kernel/security`、`../../kernel/debug`、`../automotive`、`../robot`、`../../platform/dma-engine`

---

### 环 9：证据 —— 不可观测的系统无法被治理

**本质**：系统里发生的事没留痕就等于没发生，且无法复现。

**具体体现**：

- printk、ftrace、kprobe、tracepoint、性能计数器。
- FPGA ILA、信号探测。
- crash dump、时间戳、事件日志。

**不闭合的后果**：

- 现场偶发 bug 无 trace 无 dump：每次现象不同，永远修不好。
- 性能问题无计数器：靠猜。
- 认证要求可追溯：无证据直接不过。

**必须回答的子问题**：

1. 哪些关键事件必须留痕（时间戳 + 上下文）？
2. crash dump 的格式和落点？掉电是否保留？
3. 关键路径的性能计数器有哪些？
4. FPGA 侧关键信号如何探测？

**设计动作与验证**：

- 产出 trace 点位表 + dump 格式 + 计数器清单，在设计期就布入。
- 关键事件统一时间戳。
- 验证：故障复现测试、dump 解析、计数器核对。

**模块**：`../../kernel/debug`、`../../foundation/debug-log`、`../../fpga/debug`、`../../platform/soc-arch`

---

### 环 10：演进 —— 系统持续变化，变化必须可追溯、可回退

**本质**：寄存器定义、设备树、驱动、文档、测试，任何一处改动必须同步，否则漂移。

**具体体现**：

- 单一数据源（SVD/IP-XACT/YAML 生成寄存器头 + 设备树片段）。
- OTA、A/B 槽、版本兼容矩阵。
- 问题复盘进入防复发清单。

**不闭合的后果**：

- 改寄存器定义，设备树/驱动/文档/测试不同步：隐性 bug。
- OTA 升级失败无回退：设备变砖。
- 同类问题反复发生：复盘没有闭环。

**必须回答的子问题**：

1. 每个关键配置的单一数据源在哪？生成物如何校验？
2. OTA 的升级/回滚/防变砖机制是什么？
3. 硬件版本 vs 固件版本的兼容矩阵是什么？
4. 问题复盘如何变成测试项或设计规则？

**设计动作与验证**：

- 生成器 + CI 漂移检查（生成物 diff）。
- OTA 状态机 + 回滚槽。
- 验证：生成物确定性 diff、OTA 升级/回滚演练、复盘闭环检查。

**模块**：`../../platform/devicetree-bsp`、`../../driver/pac-hal`、``、`../../ai/mlops`

## 3. 三个运行态如何在这条链上闭环

### 3.1 正常态

```text
事件进入(4) → 数据流动(5) → 并发正确(6) → 资源分配(7) → 事件完成
```

判据：事件不丢、数据不脏、顺序正确、延迟不超时、状态可观测。

### 3.2 压力态

```text
资源竞争(7) → 触发降级/回收 → 高优先级保持可用 → 水位回落
```

判据：降级是设计出来的，不是崩出来的；回收有边界，不破坏关键任务。

### 3.3 故障态

```text
异常发生(8) → 检测/隔离/恢复 → 记录证据(9) → 更新规则(10) → 防复发
```

判据：故障不静默；恢复不扩大故障域；同一故障复发必须触发规则更新。

## 4. 如何使用这份问题链

1. **新增模块前**，先回答："我挂在问题链的哪一环？我的上游环节闭合了吗？"
2. **架构评审时**，按链从 0 到 10 走查，而不是按领域列举。
3. **修改设计时**，检查该修改会冲击下游哪几环，并同步更新它们的契约。
4. **定位问题时**，先判断问题属于哪一环，再沿上下游找根因。
5. **验收时**，每一环都必须有对应的验证证据，证据链闭合才算完成。

### 5.2 每一环的模块串联

#### 环 0：物理真相

- **主模块**：`../../platform/soc-arch`、`../../platform/clock-power`、`../../fpga/timing`、`../../fpga/cdc`
- **参与模块**：`../../platform/uboot`（DDR 训练）、`../../boot/startup`（复位向量）
- **串联**：
  - `../../platform/soc-arch` 定义基址与子系统拓扑，是 `../../platform/clock-power` 建立时钟树的前提；
  - `../../platform/clock-power` 输出的"时钟稳定/复位释放"契约，是 `../../boot/startup` 敢初始化 `.data/.bss` 的前提；
  - `../../fpga/timing` 与 `../../fpga/cdc` 负责 FPGA 侧跨时钟域的物理时序，`../../platform/soc-arch` 与 FPGA 之间的接口必须遵守其结果。

#### 环 1：启动

- **主模块**：`../../boot/startup`、`../../platform/uboot`
- **参与模块**：`../../platform/devicetree-bsp`（加载 DTS）、`../../fpga/ps-pl-soc`（软硬核协同）、`../../foundation/rust-cross-build`（链接脚本）
- **串联**：
  - `../../boot/startup` 依赖环 0 的时钟复位契约；
  - `../../platform/uboot` 完成 DDR 训练与安全启动校验后，把控制权交给 `../../boot/startup`；
  - 启动完成后建立的 MMU/cache 视图，是环 2 模块工作的前提。

#### 环 2：可见性

- **主模块**：`../../memory/memory-model`、`../../memory/memory-barrier`、`../../kernel/mm`、`../../kernel/dma`
- **参与模块**：`../../platform/soc-arch`（Memory Map）、`../../foundation/rust-ffi`（ABI）
- **串联**：
  - `../../memory/memory-model` 定义段、对齐、端序，是 `../../kernel/mm` 建立页表与 `../../kernel/dma` 配置 IOMMU 的基础；
  - `../../memory/memory-barrier` 提供 MMIO 与 DMA 内存的访问序，是环 3 `../../driver/bit-register` 正确读写寄存器的前提。

#### 环 3：控制

- **主模块**：`../../driver/bit-register`、`../../driver/hal`、`../../driver/pac-hal`、`../../platform/driver-dev`
- **参与模块**：`../../kernel/device-model`、`../../kernel/platform-driver`、`../../kernel/char-device`、`../../foundation/result`、`../../foundation/misra`、`../../foundation/rust-unsafe`
- **串联**：
  - `../../driver/bit-register` 提供字段读写原语，被 `../../driver/hal` 与 `../../driver/pac-hal` 复用；
  - `../../driver/hal` 的抽象接口被 `../../kernel/platform-driver` 与 `../../kernel/char-device` 消费；
  - 寄存器写"生效"的确认，依赖 `../../foundation/result` 的错误传播与 `../../foundation/misra` 的安全返回码规范；
  - 控制建立后，外设才能被使能产生事件，进入环 4。

#### 环 4：事件

- **主模块**：`../../platform/gic`、`../../kernel/irq`、`../../concurrency/interrupt-critical`、`../../platform/gpio-pinctrl`
- **参与模块**：`../../kernel/realtime`（中断线程化）、`../../kernel/workqueue`、`../../concurrency/rtic`
- **串联**：
  - `../../platform/gic` 提供中断路由，`../../kernel/irq` 负责上半部/下半部调度；
  - `../../concurrency/interrupt-critical` 提供 ISR 里的原子与 SPSC 队列，用于把事件安全投递给主循环；
  - 中断响应产生的"DMA 完成/数据就绪"信号，是环 5 数据搬运的触发源。

#### 环 5：数据

- **主模块**：`../../platform/dma-engine`、`../../platform/mipi-csi`、`../../platform/video-codec`、`../../platform/pcie-usb-storage`、`../../ai/vision-pipeline`、`../../fpga/fifo`、`../../fpga/axi`、`../../fpga/serdes`、`../../memory/resource-scheduling`、`../../memory/memory-pool`、`../../memory/allocator`
- **参与模块**：`../../memory/ownership`、`../../kernel/block-device`、`../../kernel/net-device`、`../../foundation/move-semantics`
- **串联**：
  - `../../memory/memory-pool` 与 `../../memory/allocator` 提供 buffer，`../../memory/resource-scheduling` 决定 buffer 的配额与所有权；
  - `../../platform/dma-engine` 在 `../../platform/mipi-csi`（采集）→ `../../ai/vision-pipeline`（推理）→ `../../platform/video-codec`（编码）之间搬运数据；
  - `../../fpga/axi` 是 FPGA 侧的数据总线，`../../fpga/fifo` 提供跨时钟域缓冲，`../../fpga/serdes` 负责高速外发；
  - 数据所有权迁移过程中，`../../memory/ownership` 保证无悬垂、无双写，进入环 6 的并发约束。

#### 环 6：并发

- **主模块**：`../../concurrency/fsm`、`../../concurrency/fsm-event`、`../../concurrency/rtos`、`../../concurrency/async`、`../../kernel/lock`
- **参与模块**：`../../concurrency/interrupt-critical`、`../../memory/memory-barrier`、`../../memory/ownership`、`../../foundation/raii`
- **串联**：
  - `../../kernel/lock` 提供自旋锁/互斥/RCU，`../../foundation/raii` 提供锁守卫防泄漏；
  - `../../concurrency/fsm` 与 `../../concurrency/fsm-event` 把并发状态显式建模成状态机；
  - `../../memory/memory-barrier` 决定共享变量的可见顺序，`../../memory/ownership` 决定谁能写；
  - 并发正确性直接决定环 7 的调度能否满足实时 deadline。

#### 环 7：资源

- **主模块**：`../../kernel/scheduler`、`../../kernel/realtime`、`../../platform/npu`、`../../ai/performance`
- **参与模块**：`../../platform/gpu-multimedia`、`../../platform/clock-power`（DVFS/热）、`../../ai/npu-runtime`、`../../ai/framework`
- **串联**：
  - `../../kernel/scheduler` 与 `../../kernel/realtime` 决定 CPU 核与优先级分配；
  - `../../platform/npu` 提供算力，`../../ai/npu-runtime` 与 `../../ai/framework` 决定多模型分时；
  - `../../ai/performance` 度量延迟/吞吐/功耗，反馈给 `../../platform/clock-power` 做 DVFS 决策；
  - 资源在压力下被耗尽的边界，是环 8 故障检测的输入。

#### 环 8：故障

- **主模块**：`../../kernel/security`、`../automotive`、`../robot`
- **参与模块**：`../../foundation/misra`、`../../kernel/debug`、`../../platform/dma-engine`（DMA 错误）、`../../ai/security`
- **串联**：
  - `../../kernel/security` 提供隔离与加固，是故障不扩散的边界；
  - `../automotive` 与 `../robot` 定义 fail-safe/fail-operational 的安全态；
  - 故障必须留下证据，输出给环 9 的观测模块。

#### 环 9：证据

- **主模块**：`../../kernel/debug`、`../../foundation/debug-log`、`../../fpga/debug`、`../../fpga/verification`
- **参与模块**：`../../ai/security`
- **串联**：
  - `../../foundation/debug-log` 提供日志分级/断言/崩溃转储，`../../kernel/debug` 提供 ftrace/kprobe；
  - `../../fpga/debug` 与 `../../fpga/verification` 提供硬件侧观测与仿真证据；
  - 证据进入环 10，驱动复盘与规则更新。

#### 环 10：演进

- **主模块**：`../../platform/devicetree-bsp`、``、`../../ai/mlops`
- **参与模块**：`../../ai/quantization`（模型版本）、`../../driver/pac-hal`（寄存器生成）
- **串联**：
  - `../../platform/devicetree-bsp` 作为硬件配置的单一数据源；
  - `` 治理文档/契约的变更与追溯；
  - `../../ai/mlops` 管理模型版本、A/B、回滚；
  - 演进产生的变更，反向冲击环 0~9，需要全链重新验证。
