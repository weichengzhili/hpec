# 资源调度

> 模块目录：`memory/resource-scheduling/` · 接口文件：`include/resource_scheduler.h`

## 0. 问题定位

- **解决什么问题**：有限内存资源在多消费者竞争下如何准入、配额、回收，保证关键任务不饿死。
- **边界标准**：
  1. 准入判断有界（无动态分配），最坏复杂度明确（硬约束）。
  2. 关键消费者预留额度不被低优先级挤占（硬约束）。
  3. 回收有边界，不回收关键资源（硬约束）。
- **系统位置**：环 5；`memory-pool` → 本模块 → `dma-engine`、`scheduler`；横切环 7。

## 1. 模块定位与目标

在多任务、多流、多核共享有限内存的平台中，提供确定性的内存资源**准入、配额、预留、回收与隔离**机制。它解决的是“谁可以使用多少内存、何时可以升级使用、内存紧张时回收谁”的问题，而不是具体的块分配算法。

**边界**：

- 不负责底层分配算法，固定块池见 `memory/memory-pool`，C++ 分配器见 `memory/allocator`。
- 不负责 CPU 任务调度，任务调度见 `concurrency` 与 `kernel/scheduler`。
- 不负责语言级所有权安全，所有权与借用见 `memory/ownership`。
- 本模块位于分配器之上，对资源使用进行策略控制和审计。

**服务场景**：工业网关多路连接缓冲、汽车域控安全相关任务内存预留、AI 边缘节点推理缓冲区分级、FPGA DMA 缓冲区共享、RK3588 多核内存资源隔离。

## 2. 需求与约束

| 类别 | 要求 |
|------|------|
| 确定性 | 准入判断与回收路径必须有明确最坏执行时间 |
| 隔离性 | 高优先级任务不得因低优先级任务耗尽内存而失效 |
| 可预算 | 每个消费者必须有静态配额、预留额度和高水位统计 |
| 可审计 | 每次资源获取、释放、回收都可追踪归属 |
| 可降级 | 非关键业务在内存压力下可被限流或回收 |
| 无隐式分配 | 调度器自身不得在运行期动态申请内存 |
| 多平台 | 覆盖 MCU、RK3588、Linux/PREEMPT_RT、No std Rust 侧接口约定 |

## 3. 架构设计

### 3.1 核心概念

| 概念 | 说明 |
|------|------|
| 资源（resource） | 一类受控内存资源，如 DMA 池、固定块池、共享缓冲区池 |
| 消费者（consumer） | 任务、线程、中断下半部、AI 推理流、网络会话组等资源使用方 |
| 预留（reserved） | 为消费者保证的最低额度，安全关键任务必须配置 |
| 配额（quota） | 消费者允许使用的硬上限，超过则拒绝、降级或触发回收 |
| 令牌（token） | 一次成功准入后返回的句柄，包含资源、消费者、大小和标志 |
| 回收（reclaim） | 内存压力下按策略回收可降级、可回收的低优先级资源 |

### 3.2 逻辑结构

```
消费者 A ─┐
消费者 B ─┼─> 准入控制 ─> 配额检查 ─> 容量检查 ─> 回收策略 ─> 底层分配器
消费者 C ─┘        │            │            │            │
                   └── 审计 ────┴── 高水位 ───┴── 归属追踪 ─┘
```

### 3.3 准入判断

一次资源请求 `bytes` 需要同时满足：

1. 消费者存在且处于启用状态。
2. `consumer.used + bytes <= consumer.quota`。
3. `resource.used + bytes <= resource.capacity - resource.safety_margin`。
4. 若请求失败，按配置执行拒绝、回收后再试或降级分配。
5. 若标记为关键资源，则不得被抢占回收。

### 3.4 调度策略

| 策略 | 行为 | 适用场景 |
|------|------|----------|
| `FIXED` | 按静态配额准入，不做抢占 | MCU、功能安全分区 |
| `PRIORITY` | 高优先级可触发低优先级回收 | 实时任务 + 后台任务混跑 |
| `WEIGHTED` | 按权重分配可用额度 | 多路流媒体、AI 多推理流 |

### 3.5 资源状态

| 状态 | 含义 |
|------|------|
| 正常 | 可用容量充足，按配额准入 |
| 压力 | 可用容量低于阈值，只允许关键或高优先级请求 |
| 回收 | 正在按策略回收可回收资源 |
| 拒绝 | 无法满足配额或容量约束，显式失败 |

## 4. 接口设计

| 接口 | 说明 |
|------|------|
| `mem_rs_init(sched, resources, count, consumers, count, policy)` | 初始化调度器，校验静态配置 |
| `mem_rs_set_quota(sched, consumer_id, reserved, quota, on_pressure)` | 设置消费者预留、配额与压力策略 |
| `mem_rs_acquire(sched, resource_id, consumer_id, bytes, flags, token)` | 请求资源，返回带归属的令牌 |
| `mem_rs_release(sched, token)` | 释放令牌对应资源并更新统计 |
| `mem_rs_reclaim(sched, resource_id, want_bytes)` | 主动触发一次可回收资源回收 |
| `mem_rs_available(sched, resource_id, consumer_id)` | 查询指定消费者当前可用额度 |
| `mem_rs_stats(sched, resource_id, stats)` | 读取容量、占用、高水位等统计 |
| `mem_rs_verify(sched)` | 校验配置、令牌归属和统计一致性 |

**令牌字段**：`magic`、`resource_id`、`consumer_id`、`bytes`、`flags`、`handle`。  
`magic` 用于检测伪造或重复释放，`handle` 指向底层分配器返回的实际内存句柄。

## 5. 关键流程与时序

### 5.1 获取资源

```text
acquire()
  -> 查找 resource / consumer
  -> 校验 consumer.enabled
  -> 检查 consumer 配额
  -> 检查 resource 容量与安全余量
  -> 不足时按策略回收低优先级资源
  -> 调用 resource.alloc 回调
  -> 填充 token
  -> 更新 used / high_water
```

### 5.2 释放资源

```text
release(token)
  -> 校验 token.magic
  -> 校验 resource_id / consumer_id
  -> 调用 resource.free 回调
  -> 更新 consumer.used 与 resource.used
  -> 清除 token.magic
```

### 5.3 内存压力处理

- 关键资源：不回收，准入失败时直接返回错误。
- 可回收资源：按优先级从低到高回收，直到满足请求或达到回收上限。
- 可降级资源：返回较小额度或切换到低分辨率/低缓存模式，由上层确认。

## 6. 设计决策与权衡

| 决策点 | 选择 | 备选 | 理由 |
|--------|------|------|------|
| 调度器内存 | 静态表驱动 | 运行期动态创建 | 避免不可预测分配 |
| 配额控制 | 按消费者硬配额 | 全局先到先得 | 防止单任务耗尽资源 |
| 抢占方式 | 回收可降级资源 | 强制释放任意资源 | 降低破坏实时任务的风险 |
| 失败语义 | 显式返回错误码 | 静默降级 | 上层可审计、可决策 |
| 归属追踪 | 令牌携带消费者 ID | 仅统计总量 | 支持泄漏定位和安全审计 |
| 锁定策略 | 外部锁回调 | 调度器内置锁 | 适配裸机、RTOS、Linux |

## 7. 性能指标（KPI）

- 准入判断最坏路径为有界遍历，不依赖堆分配。
- 消费者与资源数量按静态表配置，查找复杂度不高于 \(O(n)\)。
- 配置校验必须在启动阶段完成：`Σ reserved <= capacity - safety_margin`。
- 记录每类资源的峰值占用率，建议长期稳定低于 80%。
- 回收延迟上界由可回收对象数量、单次回收耗时和最大回收字节数共同限定。
- 令牌校验失败次数、配额拒绝次数、回收次数均可统计。

## 8. 可靠性设计

- 启动自检：资源容量、安全余量、消费者 ID 唯一性、预留总额度。
- 令牌防护：魔数校验、双重释放检测、消费者归属校验。
- 水位监控：消费者和资源的 `high_water` 用于容量规划。
- 压力降级：达到阈值后限制非关键消费者准入，避免雪崩。
- 故障隔离：底层分配器失败不得破坏调度器内部统计。

## 9. 安全设计

- 安全关键消费者配置独立预留额度，禁止被低优先级任务挤占。
- 关键资源标记 `MEM_RS_F_CRITICAL`，不参与自动回收。
- DMA 等共享资源必须记录消费者归属，避免跨分区越权释放。
- 回收路径必须由资源提供方显式实现，调度器不直接操作未知内存。
- 敏感缓冲区释放前由底层资源回调执行清零。

## 10. 测试与验证策略

- 配额测试：验证超限请求被拒绝，且不影响其他消费者额度。
- 优先级测试：构造低优先级占用，验证高优先级请求可触发回收。
- 关键资源测试：验证关键资源不被回收、不被降级。
- 令牌测试：验证伪造令牌、重复释放、跨消费者释放均能检测。
- 压力测试：长时间随机申请/释放，检查高水位、统计一致性和泄漏。
- 故障注入：底层分配失败、回收失败、配额配置非法时返回明确错误码。

## 11. 集成与部署

- 在启动阶段通过静态表注册资源与消费者。
- 配额和预留额度来自系统预算表，纳入设计评审与版本管理。
- 与 `memory/memory-pool` 配合时，资源容量对应固定块池容量。
- 与 `kernel` 或 RTOS 配合时，锁回调映射到内核锁或临界区保护。
- 与 `system` 场景配合时，每个场景维护独立的资源预算配置。
